
## Goal

Produce a standalone markdown document (`docs/SUPABASE_INTEGRATION.md`) that captures exactly how this project connects to Supabase, so the same setup can be replicated in another project.

## Where the doc comes from (evidence in this codebase)

- **Client SDK bootstrap**: `src/integrations/supabase/client.ts` creates a single `@supabase/supabase-js` client with `persistSession`, `autoRefreshToken`, and `localStorage`. This file is auto-generated by the Lovable ↔ Supabase connection.
- **Env vars** (`.env`, injected by the Lovable Cloud / Supabase connection, consumed by Vite at build time):
  - `VITE_SUPABASE_URL`
  - `VITE_SUPABASE_PUBLISHABLE_KEY` (anon key — safe to ship)
  - `VITE_SUPABASE_PROJECT_ID`
- **Generated types**: `src/integrations/supabase/types.ts` (never hand-edit; regenerated from live schema).
- **Usage pattern** in app code: `import { supabase } from "@/integrations/supabase/client"` (see `LikeDislikeButtons.tsx`, `RemindMeButton.tsx`, `History.tsx`, etc.) — used for `auth.getSession/getUser`, `onAuthStateChange`, and `.from(table).select/insert/update/delete`.
- **Auth model**: email + password only, session in `localStorage`, listener via `supabase.auth.onAuthStateChange`.
- **Server-side (Edge Functions)**: under `supabase/functions/*`, configured in `supabase/config.toml` with per-function `verify_jwt` flags. Secrets (`TMDB_ACCESS_TOKEN`, `SMTP_*`, `SUPABASE_SERVICE_ROLE_KEY`, etc.) are read via `Deno.env.get(...)` — never in the frontend bundle.
- **Data access**: every user table has RLS enabled and `GRANT`s to `authenticated` / `service_role` (see project schema).

## Document outline (`docs/SUPABASE_INTEGRATION.md`)

1. **Overview** — what Supabase provides here (Auth, Postgres + RLS, Edge Functions, Secrets).
2. **Prerequisites** — a Supabase project (or a Lovable Cloud-managed one), Node 18+, `@supabase/supabase-js` v2.
3. **Environment variables** — the three `VITE_SUPABASE_*` values, where they come from, and the rule that only the *anon/publishable* key ever ships to the browser. `service_role` stays server-side.
4. **Frontend client setup** — full copy of `src/integrations/supabase/client.ts` as the template, plus the recommended folder layout (`src/integrations/supabase/{client.ts,types.ts}`) and the `@/integrations/supabase/client` import alias (requires `vite.config.ts` `@` alias to `./src`).
5. **Typed schema** — how `types.ts` is generated (`supabase gen types typescript --project-id <ref>`), and the rule to never edit it manually.
6. **Auth usage patterns** — sign up / sign in / sign out snippets, `getSession`, `onAuthStateChange` cleanup, and the "check session in `useEffect`, redirect if null" pattern used by `History.tsx`.
7. **Database access patterns** — `.from(table).select().eq(...)`, `.insert`, `.update`, `.delete`, `.maybeSingle()`, and error handling via the shared `logger`.
8. **RLS & GRANT recipe** — the mandatory 4-step migration order (`CREATE TABLE` → `GRANT` → `ENABLE RLS` → `CREATE POLICY`) with a copy-paste template for a user-owned table.
9. **Edge Functions** — folder layout `supabase/functions/<name>/index.ts`, `supabase/config.toml` entry with `verify_jwt`, JWT validation via `supabase.auth.getClaims(token)`, secret access via `Deno.env.get`, and CORS headers.
10. **Secrets management** — list of secret names this project uses, where they're stored (Supabase project secrets, not `.env`), and how Edge Functions read them.
11. **Replication checklist** — step-by-step to reproduce in a new project: create Supabase project → connect in Lovable (or set env vars manually) → copy `client.ts` template → run migrations with GRANTs+RLS → generate `types.ts` → add Edge Functions + `config.toml` → configure secrets.
12. **Security do/don't** — never expose `service_role`, never store roles on `profiles` (use separate `user_roles` table + `has_role` SECURITY DEFINER function), always use the `logger` wrapper, RLS on every public table.
