# Supabase Integration Guide

This document explains exactly how this project (BingeGuide) connects to Supabase, so the same setup can be replicated in another Vite + React + TypeScript project.

It covers: the client SDK, environment variables, typed schema, auth patterns, database access, Row Level Security (RLS), Edge Functions, and secrets.

---

## 1. Overview

Supabase provides four things to this app:

| Capability      | Where it lives                                     |
| --------------- | -------------------------------------------------- |
| Authentication  | `supabase.auth` (email + password only)            |
| Postgres DB     | `public.*` tables, accessed via PostgREST + RLS    |
| Edge Functions  | `supabase/functions/<name>/index.ts` (Deno)        |
| Secrets         | Supabase project secrets, read via `Deno.env.get`  |

The frontend talks to Supabase directly using the **anon (publishable) key**. Anything privileged (TMDB API key, SMTP credentials, `service_role` key) stays inside Edge Functions.

---

## 2. Prerequisites

- A Supabase project (or a Lovable-Cloud-managed one).
- Node 18+ and a Vite + React + TypeScript app.
- Dependency: `@supabase/supabase-js` v2.

```bash
npm i @supabase/supabase-js
```

---

## 3. Environment variables

Vite injects these at **build time**. They live in the project-root `.env` (auto-populated when you connect Supabase in Lovable):

```env
VITE_SUPABASE_URL="https://<project-ref>.supabase.co"
VITE_SUPABASE_PUBLISHABLE_KEY="<anon-key-jwt>"
VITE_SUPABASE_PROJECT_ID="<project-ref>"
```

Rules:

- Only the **anon / publishable** key ever ships to the browser. It is designed to be public — RLS protects the data.
- The **`service_role` key is server-only**. Never put it in `.env` of a client-side SPA; store it as a Supabase Edge Function secret.
- If `.env` is missing at publish time, the client initializes with `undefined` and the site breaks silently. Restore the values — do not blank them.

## 4. Frontend client setup

Recommended folder layout:

```
src/integrations/supabase/
├── client.ts   # single shared Supabase client
└── types.ts    # generated Database types (do not hand-edit)
```

**`src/integrations/supabase/client.ts`** — the exact template used here:

```ts
// This file is automatically generated. Do not edit it directly.
import { createClient } from '@supabase/supabase-js';
import type { Database } from './types';

const SUPABASE_URL = "https://<project-ref>.supabase.co";
const SUPABASE_PUBLISHABLE_KEY = "<anon-key-jwt>";

// Import the supabase client like this:
// import { supabase } from "@/integrations/supabase/client";

export const supabase = createClient<Database>(SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY, {
  auth: {
    storage: localStorage,
    persistSession: true,
    autoRefreshToken: true,
  }
});
```

The `@/` alias must be configured in `vite.config.ts`:

```ts
resolve: {
  alias: { "@": path.resolve(__dirname, "./src") }
}
```

Consume the client anywhere:

```ts
import { supabase } from "@/integrations/supabase/client";
```

## 6. Auth usage patterns

Email + password only in this project. Pattern used across pages (see `src/pages/History.tsx`, `src/components/LikeDislikeButtons.tsx`):

**Check session and redirect if not logged in:**

```ts
useEffect(() => {
  supabase.auth.getSession().then(({ data: { session } }) => {
    if (!session) navigate("/auth");
    else setUser(session.user);
  });
}, [navigate]);
```

**React to auth changes (always clean up the subscription):**

```ts
useEffect(() => {
  const { data: { subscription } } = supabase.auth.onAuthStateChange(
    (_event, session) => setUserId(session?.user?.id ?? null)
  );
  return () => subscription.unsubscribe();
}, []);
```

**Sign up / sign in / sign out:**

```ts
await supabase.auth.signUp({ email, password });
await supabase.auth.signInWithPassword({ email, password });
await supabase.auth.signOut();
```

Password policy enforced client-side: 8+ chars, upper, lower, number.

## 7. Database access patterns

All CRUD flows through the shared client. Always log errors via `@/lib/logger` (never raw `console.log`).

```ts
// SELECT one
const { data, error } = await supabase
  .from("user_preferences")
  .select("reaction")
  .eq("user_id", uid)
  .eq("content_id", contentId)
  .maybeSingle();

// INSERT
await supabase.from("user_preferences").insert({
  user_id: uid, content_id, content_type, reaction: "like",
});

// UPDATE
await supabase.from("user_preferences")
  .update({ reaction: "dislike" })
  .eq("user_id", uid).eq("content_id", contentId);

// DELETE
await supabase.from("reminders").delete().eq("id", reminderId);
```

Use `.maybeSingle()` when zero or one row is expected; `.single()` throws if zero.

## 8. RLS + GRANT recipe (mandatory 4-step order)

Supabase's Data API (PostgREST) does **not** grant default privileges on `public` — without `GRANT`s the app gets a permission error. Every new table must follow this order in the same migration:

```sql
-- 1. CREATE TABLE
CREATE TABLE public.notes (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id uuid NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  content text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);

-- 2. GRANT (tune to policies; drop anon if every policy scopes to auth.uid())
GRANT SELECT, INSERT, UPDATE, DELETE ON public.notes TO authenticated;
GRANT ALL ON public.notes TO service_role;

-- 3. ENABLE RLS
ALTER TABLE public.notes ENABLE ROW LEVEL SECURITY;

-- 4. POLICY
CREATE POLICY "Users manage own notes"
  ON public.notes FOR ALL
  USING (auth.uid() = user_id)
  WITH CHECK (auth.uid() = user_id);
```

**User roles** must live in a separate `user_roles` table (never on `profiles`), checked via a `SECURITY DEFINER` function `has_role(user_id, role)` to avoid recursive RLS.

## 9. Edge Functions

Layout:

```
supabase/
├── config.toml
└── functions/
    ├── tmdb-proxy/index.ts
    ├── send-contact-email/index.ts
    └── send-due-reminders/index.ts
```

**`supabase/config.toml`** — per-function JWT flag:

```toml
project_id = "<project-ref>"

[functions.tmdb-proxy]
verify_jwt = false          # public endpoint

[functions.send-contact-email]
verify_jwt = true           # requires a valid Supabase JWT
```

**Function skeleton with JWT validation and CORS:**

```ts
import { createClient } from 'npm:@supabase/supabase-js@2';

const corsHeaders = {
  "Access-Control-Allow-Origin": "*",
  "Access-Control-Allow-Headers": "authorization, x-client-info, apikey, content-type",
};

Deno.serve(async (req) => {
  if (req.method === "OPTIONS") return new Response(null, { headers: corsHeaders });

  const authHeader = req.headers.get("Authorization");
  if (!authHeader?.startsWith("Bearer ")) {
    return new Response(JSON.stringify({ error: "Unauthorized" }), { status: 401, headers: corsHeaders });
  }

  const supabase = createClient(
    Deno.env.get("SUPABASE_URL")!,
    Deno.env.get("SUPABASE_ANON_KEY")!,
    { global: { headers: { Authorization: authHeader } } }
  );

  const { data, error } = await supabase.auth.getClaims(authHeader.replace("Bearer ", ""));
  if (error || !data?.claims) {
    return new Response(JSON.stringify({ error: "Unauthorized" }), { status: 401, headers: corsHeaders });
  }

  const userId = data.claims.sub;
  // ... your logic ...
  return new Response(JSON.stringify({ ok: true }), { headers: { ...corsHeaders, "Content-Type": "application/json" } });
});
```

**Invoke from the frontend:**

```ts
const { data, error } = await supabase.functions.invoke("tmdb-proxy", {
  body: { path: "/movie/upcoming" },
});
```

## 10. Secrets management

Secrets are stored **in the Supabase project** (Dashboard → Edge Functions → Secrets), not in `.env`. Edge Functions read them via `Deno.env.get("NAME")`.

Auto-populated by Supabase:

- `SUPABASE_URL`
- `SUPABASE_ANON_KEY`
- `SUPABASE_SERVICE_ROLE_KEY` (server-only)
- `SUPABASE_DB_URL`

Project-specific secrets used here (add equivalents in the new project as needed):

- `TMDB_ACCESS_TOKEN`, `TMDB_API_KEY` — external API keys
- `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM_EMAIL` — outbound email
- `REMINDER_FUNCTION_SECRET` — shared secret between cron and function
- `RESEND_API_KEY`, `WHATSAPP_TOKEN` — optional providers

**Never store secrets in database tables.** Never expose `service_role_key` to the browser or pass it as a caller token.

## 11. Replication checklist

To reproduce this integration in a new project:

1. Create a Supabase project (or connect Lovable Cloud). Note the project ref, URL, and anon key.
2. Install the SDK: `npm i @supabase/supabase-js`.
3. Add the three `VITE_SUPABASE_*` variables to `.env`.
4. Create `src/integrations/supabase/client.ts` from the template in §4.
5. Ensure `@/` alias is set in `vite.config.ts`.
6. Write migrations following the 4-step order in §8 (CREATE → GRANT → RLS → POLICY).
7. Generate types: `npx supabase gen types typescript --project-id <ref> > src/integrations/supabase/types.ts`.
8. For any server-side logic, add an Edge Function under `supabase/functions/<name>/index.ts` and register it in `supabase/config.toml` with the appropriate `verify_jwt` flag.
9. Add required secrets in the Supabase Dashboard.
10. Import and use `supabase` from `@/integrations/supabase/client` throughout the app.

## 12. Security do / don't

**Do**

- Enable RLS on every `public` table and write policies scoped to `auth.uid()`.
- Grant `authenticated` and `service_role` explicitly; grant `anon` only for truly public tables.
- Keep third-party API calls (TMDB, SMTP, etc.) inside Edge Functions.
- Validate JWTs in Edge Functions with `supabase.auth.getClaims(token)`.
- Store roles in a separate `user_roles` table + `has_role()` `SECURITY DEFINER` function.
- Use the project logger (`@/lib/logger`) so nothing leaks in production.

**Don't**

- Don't ship `service_role_key` to the browser or pass it as a caller token.
- Don't store roles on `profiles` (privilege-escalation risk).
- Don't hand-edit `src/integrations/supabase/types.ts`.
- Don't skip `GRANT` when creating a table — RLS alone is not enough.
- Don't put secrets in database rows or in the committed `.env`.
